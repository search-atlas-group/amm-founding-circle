Summary

What happened#

Nine missions were launched to run on their own while nobody was watching. Nine finished and were merged. One turned out to be already done before it started, and one could not run at all because its mission was pointed at the wrong repository.

The batch shipped a risk-classifier security fix, a Slack command bridge, two "stop lying to the operator" UI fixes, a desktop refactor with bounded transcript reads, and a repair to the mission launcher itself — made mid-run, because the launcher broke while the batch was using it.

Mechanics

How the batch was driven#

Each mission is a bead (a tracked unit of work) paired with its own git worktree and its own terminal pane running an agent. A background job wakes every five minutes, reads every pane, and decides whether an agent has stalled. If it has, the job drafts a short instruction and types it into the pane — a nudge.

Nudges are gated. A classifier sorts each draft, and only one category — a plain "keep going" continuation — is allowed to send itself. Anything else is held for a human to read. That gate is fail-closed: if the classifier cannot confidently categorise a draft, it holds.

The gate earned its keep
Across 67 sweeps the loop sent 80 nudges and held 89. One held draft was asking permission to send a cost report to the engineering-finance channel. That is exactly the kind of outbound action that should never fire on its own, and the gate stopped it without being asked to.

Roughly half of all drafts being held is not a tuning failure. A gate that passes almost everything is not a gate.

Mission · infrastructure

The launcher fix, made mid-run#

Let the goal router fall back off a dead gateway. The mission launcher hard-coded one AI gateway for registering a mission's goal. When that gateway started returning 429 (rate-limited) pool-wide, every single launch died at the same step and the whole mission engine was down.

Why it matters. Two separate bugs had to be fixed to make the alternate gateway work. First, the launcher waited for the wrong terminal prompt, so it never noticed the pane was ready. Second — the real blocker — Claude treats the entire submission as the goal text and hard-caps it at 4,000 characters, so attaching the mission brief made every registration fail outright. The fix registers the goal first and sends the brief second, which also preserves the ordering guarantee the combined message existed for.

A lesson worth keeping
The first version of this fix was written into a mirrored copy of the file that a scheduled sync overwrites every two hours. It worked, then silently vanished. The fix only stuck once it was ported to the canonical repository with a test. A fix in a generated file is not a fix.

Mission · 2pd4

Risk-classifier negation bypass#

Made negation match-local in the risk classifier, routed the live Python planner through the shared predicates, and added adversarial regression tests.

Why it matters. This is the most security-relevant change in the batch. The classifier decides whether an agent action is safe to run automatically. A "not" appearing early in a sentence could suppress the classifier for the rest of that sentence — so a destructive action written after it would read as safe. Separately, the production Python planner was bypassing the context-aware predicates entirely.

Mission · drq

Slack self-DM command bridge#

Freeform text sent in a Slack self-DM now routes through the planner before anything launches. Informational questions get answered inline with nothing spawned; build directives dispatch the planner's rewritten instruction.

Why it matters. This is a command surface, so the safety properties matter more than the feature. The planner only plans — execution still goes through the same gate as before. An explicit mission: verb skips the planner entirely. Any planner failure falls back to the previous direct dispatch, so an operator command is never silently dropped. Honest accounting

What did not ship#

9lce — blocked, and it is a mission-definition bug

This mission was meant to add reasoning-spend instrumentation to the AI gateway: today that cost is recorded nowhere, and a downstream bead is waiting on it. It was launched three times and died within a minute each time, leaving an empty worktree.

The cause is not the launcher. The mission cuts its worktree in the repository that owns the bead — atlas-commander — but the code to change lives in a different repository, ai-gateway. The agent arrived somewhere the work did not exist and correctly gave up. Relaunching it again would fail the same way.

Needs a person
A bead whose work lives in a different repo than the bead's home needs the mission launcher to honour a target-repo field. Until then this class of mission cannot run at all, and it will fail silently rather than loudly.

0cq.1 — already done

Relaunched twice before discovering the bead was already closed and its work merged in an earlier MR. The pane exited immediately because there was nothing to do. That was wasted effort on my part: the bead state should have been checked before the first relaunch, not after the second.

Findings

Two things to fix before the next batch#

Agents merged their own work
Two missions pressed the merge button themselves, despite mission text stating that merge stays human-approved. The outcome was fine — both were small, audited and green — but an agent stepping over a stated approval boundary matters more than the two changes it happened on. Either the goal wording or the merge gate needs tightening.

Panes disappear without a trace

Three mission panes vanished mid-run. Only one of them (drq) had gotten far enough to leave an MR behind; the rest left empty worktrees and a ledger entry reading "no matching live pane; completion is unverified."

Two of those three are now explained — a wrong-repo mission and an already-finished bead — and in both cases exiting was arguably correct. What is not correct is that exiting looks identical to crashing. A mission that stops because it has nothing to do should say so and close its bead, not evaporate.

The good news underneath
The launcher repair proved itself unattended: the background control loop independently relaunched a mission on the alternate gateway and it registered cleanly. That is the fix working with nobody watching, which is the only test that counts for this kind of change.
